# Migration to 0.8.0

## What changes

- **One branch carries a request from the first draft to the merge.** Before: the
  spec was discussed on a `req/REQ-0012-<slug>` branch, which was merged into
  `develop` when the developer approved it; the request then waited as `ready` on
  `develop` until `/ss-workflow:check-req` claimed it on a second branch,
  `feat/REQ-0012-<slug>`. Now: `/ss-workflow:new-req` creates
  `feat/REQ-0012-<slug>` from `develop` for the draft, the approval is a commit on
  that branch, and the implementation and the review continue on it. `develop` gets
  the request only with the merge, already in `reqs/done/`. A hotfix is discussed on
  `hotfix/REQ-0012-<slug>` and moves to `hotfix/<name>-v<version>` when it starts.
- **The approval can start the implementation at once.** Before: after the approval,
  the developer ran `/ss-workflow:check-req`, read the overview, and picked the
  request. Now: the approval asks "start now" or "start later". "Start now" hands
  over to `/ss-workflow:check-req REQ-0012`, which starts that request without the
  overview. "Start later" keeps it `ready` on its branch.
- **check-req recommends what to work on next, including unfinished work.** Before:
  without a request id, `/ss-workflow:check-req` offered only `ready` requests, and an
  `in-progress` request could be resumed from the root checkout only by naming it.
  Now: it offers `ready` and `in-progress` requests together and recommends one:
  hotfixes first, then dependencies, `priority`, unfinished before new, rework sent
  back by a review, and the older id. Choosing an `in-progress` request resumes it in
  its worktree, or recreates the worktrees first.
- **Fewer commits during the discussion.** Before: every round of the discussion was
  a commit and a push. Now: the draft is committed when it is created, when the
  developer pauses it, and when the developer approves it.
- **No claim race.** Before: the workspace branch was the claim, and across machines
  the first pushed claim commit won. Now: the branch exists since the draft, and
  starting is a plain commit (`chore(reqs): start REQ-0012`) that sets
  `in-progress`. Each developer usually keeps a workspace of their own; in a shared
  workspace, a pushed `in-progress` shows the others that the request is taken.
- **A dropped request** is recorded on `develop` through a short-lived
  `drop/REQ-<id>` branch instead of `req/REQ-<id>-drop`. A discarded draft leaves no
  record, as before.
- **The history of a project carries nothing of the workspace.** Before: a project
  branch had the name of the workspace branch (`feat/REQ-0012-gui-button`), every
  project commit and project merge commit ended with `Refs: <workspace>#REQ-0012`,
  and the merge requests, the release merge requests, and the changelog named the
  requests (`<workspace>#REQ-0012`). Now: the project's branch names, commits, merge
  commits, merge requests, and changelog describe the change in the project's own
  terms, with no request id, no workspace name, and no `Refs:` footer. Several
  developers may each keep a workspace of their own for the same projects, so a
  request id only means something in one workspace.
- **A project branch is named after the change.** Before: the same name in the
  workspace and in each project. Now: the workspace branch keeps
  `<type>/REQ-<id>-<slug>`, and each project of the request gets `<type>/<slug>`
  (`feat/gui-button`). Starting the request checks that this name is free in every
  project of the request, locally and on its remote, and asks for another
  descriptive name when it is taken. A hotfix keeps `hotfix/v<version>` in the
  project.
- **The request file records its project branch.** A new frontmatter key
  `project-branch`, after `branch`, holds it once the request is started. The skills
  find a request's project branches only through it, never by a name pattern, and
  leave every other branch in a project alone: it may be another developer's work.
- **The release finds outside changes through the requests.** Before: a project
  commit without a `Refs:` footer counted as a change made outside the workspace.
  Now: the project merge commits that the closed requests record in their
  `Merged into develop` note are this workspace's changes, and every other commit on
  the first-parent line of the project's develop branch is a change from outside it,
  for example from a teammate's own workspace.

## Steps

1. **Managed blocks**: the upgrade re-renders "Working agreement", "Workspace and
   projects", "Branching model", "Remote and pushing", and "Commit convention" in
   root `AGENTS.md`, and "Files", "Request file format", and "Lifecycle" in
   `reqs/AGENTS.md`. Nothing to do here.
2. **Request files and branches**: do not change them. The skills still read the old
   places:
   - A draft on a `req/REQ-<id>-<slug>` branch stays there. `/ss-workflow:new-req`
     renames the branch to `<type>/REQ-<id>-<slug>` the next time it continues the
     draft.
   - A `ready` request in `reqs/` on `develop` stays there. Starting it creates its
     branch from `develop`, as before, and adds `project-branch:`.
   - A request that is started already has no `project-branch` on its workspace
     branch: the skills then use the name of its workspace branch in the projects,
     so its project branches keep working as they are. Do not rename a project
     branch: it may be pushed, and other people may have checked it out.
   - A hotfix started before 0.8.0 left an old copy in `reqs/` on `develop`; its
     merge into `develop` still removes it.
3. **Project history**: do not change it. Commits that already end with
   `Refs: <workspace>#REQ-xxxx`, and changelog entries that name requests, stay as
   they are: published history is never rewritten. New commits follow the new rule.
4. **Text that the developer owns**: search root `AGENTS.md` outside the managed
   blocks ("Project notes" and the other sections), `src/AGENTS.md` outside its
   managed blocks (the `## Project: <name>` sections), and the README files for
   rules that ask for the old project references:
   `grep -n "Refs: .*#REQ\|#REQ-" AGENTS.md src/AGENTS.md README*.md`. Show each hit,
   and propose to remove the reference or to reword the rule. Change it only when the
   developer agrees. Already done when the search finds nothing, or the developer
   kept the hits.

## Check

- The "Commit convention" block of root `AGENTS.md` no longer contains

- `git status --porcelain -- reqs/` shows no changed request file, only
  `reqs/AGENTS.md`.
- No project repository changed: `git -C src/<name> status --porcelain` is empty, and
  its branches are the same as before the upgrade, for every project.
