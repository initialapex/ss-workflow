# Migration to 0.9.1

## What changes

- **A converted Visual Studio project has its solution at the root.** Before: the
  conversion of a repository from ss-workflow 0.5.0 and older
  (`references/convert-legacy.md`) could leave the old wrapper folders in place, so
  the project in the workspace looked like `projects/SSDisp/src/SSDisp.sln`, with the
  tests in `projects/SSDisp/tests/`. Now: the solution sits at the root of the project
  repository, with every project folder next to it, as Visual Studio creates it:
  `projects/SSDisp/SSDisp.sln`, `projects/SSDisp/SSDisp/`,
  `projects/SSDisp/SSDisp.Test/`, `projects/SSDisp/SSDisp.Sample/`. Test and sample
  projects are kept unless the developer deletes them. Other toolchains follow their
  own conventions, as before.
- **Third-party folders are the developer's choice.** The conversion asks about each
  one (`external/`): keep it in the project repository, move it to the workspace's
  `projects/` as a project of its own, remove it, or put it somewhere else.
- **This upgrade repairs a workspace that was converted with the old layout left in
  place.** It checks the project named in `legacy-project` and, when the wrapper
  folders are still there, proposes to move its files: one commit on the project's
  develop branch, and the gitlink on the workspace's `develop`. Nothing moves without
  the developer's approval. A workspace that was not converted, or whose project
  already has its toolchain's layout, has nothing to do.

## Steps

`<develop-branch>` and `<main-branch>` are the keys of the project's entry in
`projects`, and every `git -C projects/<name>` command runs in the root checkout of
the workspace.

1. **Find the project.** Read `legacy-project` in "Workflow settings" of root
   `AGENTS.md`. When it is empty, the workspace was not converted: skip the other
   steps. Otherwise fetch the project (`git -C projects/<name> fetch --prune`) and
   look at the layout of its develop branch:

   ```bash
   git -C projects/<name> ls-tree -r --name-only origin/<develop-branch> | grep -iE '\.slnx?$'
   git -C projects/<name> ls-tree -d --name-only origin/<develop-branch>
   ```

   Use the local `<develop-branch>` when the project has no remote. A Visual Studio
   project needs the repair when its solution is not at the root, or when `src/`,
   `tests/`, or `samples/` still holds a project folder. For another toolchain,
   compare the layout with what the toolchain expects, as section 3 of
   `references/convert-legacy.md` does, and ask when you cannot tell.

   Already done when the layout fits: say so, and skip the other steps.
2. **Preconditions.** Check, and stop with a list of what was found if any fails:
   - The root checkout of the workspace is on `develop`, and `git status
     --porcelain` is empty.
   - `git -C projects/<name> status --porcelain` is empty, and the project's local
     `<develop-branch>` equals its remote one (nothing to push or to pull).
   - No request of this project is started and not merged: no request branch whose
     request file says `in-progress`, `review`, or `done` while the branch is not
     merged into `develop`, and whose `projects` names `<name>` (a request without
     `projects` belongs to `legacy-project`). Collect them as `/ss-workflow:check-req`
     does in its overview. Their project branches start from the old layout, and a
     file that they add in a moved folder would land in the old place.
   - No `release/*` or `hotfix/*` branch in the project, and no `hotfix/*` branch in
     the workspace.
   - `git -C projects/<name> worktree list` shows the submodule folder only.

   Drafts and `ready` requests do not block: their project branch does not exist yet,
   and it starts from the repaired develop branch. If the preconditions fail, the
   developer finishes that work first with `/ss-workflow:review` and
   `/ss-workflow:merge`, and runs `/ss-workflow:init` again. Until then the project
   keeps working in its old layout, and the upgrade stops without recording the new
   version.
3. **Show the plan and ask.** Propose the move table of section 3 of
   `references/convert-legacy.md`, from the files of the project's develop branch:
   - For Visual Studio, the target is fixed: the solution at the root, every project
     folder next to it, and no `src/`, `tests/`, or `samples/` left. The other files
     of `src/` that the tools find by walking up (`Directory.Build.props`,
     `NuGet.config`, `.editorconfig`) move to the root too.
   - Test and sample projects are kept by default. Ask about each one: keep it, or
     delete it.
   - Ask about each third-party folder with the four choices of that section: keep
     it in the project (default), move it to the workspace's `projects/` as a
     project of its own, remove it, or other.

   Also list the texts of the workspace that name the old paths, from
   `grep -rnE "(src|tests|samples)[/\\\\]" AGENTS.md projects/AGENTS.md docs/ README*.md`:
   the project's entry in `projects` (`project-file`, `version-source`, and the
   commands), its `## Project: <name>` section in `projects/AGENTS.md`, the docs in
   `docs/<name>/`, the README files, and `agent-files` patterns. These texts belong to
   the developer: propose the new text for each hit. Continue only when the developer
   agrees to the table and to the texts.
4. **Move in the project**, on its develop branch. The submodule is checked out at
   the gitlink of `develop`, which is detached; after step 2 that commit is the tip of
   `<develop-branch>`, or `develop`'s gitlink is behind it. In the second case, ask
   first, because the workspace then takes in the commits of other people (see
   "Workspace and projects" in root `AGENTS.md`).

   ```bash
   git -C projects/<name> checkout <develop-branch>
   ```

   - For each third-party folder that moves to the workspace's `projects/`, ask for
     the new repository's URL and copy the folder's history first, as section 3 of
     `references/convert-legacy.md` shows, with `<develop-branch>` in place of
     `<base>`.
   - Apply the table as "Apply it on `develop`" in that section says: `git mv` for
     each move, `git rm -r` for each deletion, every broken path fixed (the solution,
     the project files, `ProjectReference`, the paths to third-party folders, CI
     files, and scripts), and the build and the tests run with the rewritten
     commands in `projects/<name>`. If a folder moved to the workspace's `projects/`,
     build after step 5 instead.
   - Commit in the project: `refactor: move the projects to the root of the
     <toolchain> layout`, with the path table in the body. The commit follows the
     project's commit convention: it names no request, no workspace, and no
     workspace file.

   Already done when step 1 finds that the layout fits.
5. **Record it in the workspace**, on `develop`:
   - `git add projects/<name>`: `develop`'s gitlink now records the repaired develop
     branch.
   - The texts that the developer approved in step 3, the project's entry in
     `projects` included.
   - Each third-party folder that moved to the workspace's `projects/` is added as a
     project from its new repository, as section 5 of
     `references/convert-legacy.md` says. **Add project** mode commits it on its
     own (`chore(workspace): add the <folder> project`); then build `<name>` with
     its `build-command`.

   The gitlink and the texts go into the upgrade commit of `references/upgrade.md`,
   section 4.
6. **Push** the project's develop branch as its `push-policy` allows, and before the
   workspace: a clone of the workspace has to find the commit that the gitlink
   records. Then the workspace's `develop`, as section 4 of `references/upgrade.md`
   says. The project's main branch keeps the old layout until the next release of the
   project, which merges the develop branch as usual. A later hotfix branch starts
   from the main branch, so it has the old layout too; its merge into the develop
   branch carries its changes to the moved files, because git follows the renames.
7. **Other clones.** Tell the developer what other clones of the workspace see after
   `git pull` and `git submodule update`: the project's files are at their new places.
   Ignored build output in the old folders (`src/SSDisp/bin/`, `src/SSDisp/obj/`)
   stays behind and can be deleted.

## Check

- For Visual Studio: `git -C projects/<name> ls-tree --name-only <develop-branch>`
  lists the solution, and `git -C projects/<name> ls-tree -d --name-only
  <develop-branch>` lists no `src`, `tests`, or `samples`, unless the developer kept
  one of them in the table.
- `git -C projects/<name> cat-file -e <develop-branch>:<project-file>` succeeds with
  the `project-file` of the project's entry.
- `git -C projects/<name> log --follow --oneline -- <a moved file>` still shows the
  commits from before the move.
- The project builds with its `build-command` in `projects/<name>`, and its
  `test-command` passes, or the report says which of them did not run and why.
- `git rev-parse develop:projects/<name>` is the commit of the project's
  `<develop-branch>`, and the root checkout is clean.
- Each folder that moved to the workspace's `projects/` has an entry in `projects` and
  a path in `.gitmodules`.
