# Migration to 0.13.0

## What changes

- **Every stage has a role.** Before: the skills did not say whose point of view each
  stage works from. Now: `/ss-workflow:new-req` is a requirements engineer,
  `/ss-workflow:check-req` is an engineering lead who reviews the request and then a
  software engineer who implements it, `/ss-workflow:init` is a software engineer who
  writes the initial spec, `/ss-workflow:review` is an engineering lead plus a
  specialist reviewer for each skill of the project, and `/ss-workflow:merge` and
  `/ss-workflow:release` are a CI and CD engineer. Each skill states its role at its
  top, and "Working agreement" in root `AGENTS.md` lists them.
- **The engineering lead reviews a request before it starts.** Before:
  `/ss-workflow:check-req` created the branches and worktrees of a `ready` request at
  once. Now: it first checks the approved spec (complete, small enough, ordered after
  its dependencies, evidence in order, checkable), records `### Lead review` in
  `## Notes`, and offers to send a failing spec back to `/ss-workflow:new-req` or to
  start it anyway.
- **A request that is too large is split.** Before: `/ss-workflow:new-req` proposed a
  split only when the input held independent changes. Now: "Request size" in
  `reqs/AGENTS.md` gives the signals and the three axes (importance with must-fix
  first, type, cost), and `/ss-workflow:new-req` splits a request along them so that
  one request can be read and reviewed in one sitting. A part that needs another one
  starts its "Scope" with `Depends on: REQ-xxxx`.
- **Technology comes from the skills of a project, not from the workflow.** Before: the
  detailed design of a spec was described in the terms of object-oriented code. Now:
  the project key `skills` lists the skills that apply to a project, as
  `<plugin>:<skill>` separated by commas (for example `ss-design:ood,
  ss-design:ui-ux`). `/ss-workflow:new-req` designs with them and adds the sections
  that they require ("Sections from the project's skills"), the implementation follows
  them, and `/ss-workflow:review` applies the review checklist of each one
  (`### Skill review`). The section "Types and public members" of "Detailed design" is
  now "Components and interfaces", in words that fit any kind of project. A spec that
  was written before keeps its old heading, and the skills accept it.

## Steps

1. **`skills` for every project.** For each entry in `projects` in root `AGENTS.md`
   that lacks the key, add `skills:` after `project-kind:`. Show the developer the list
   of the projects with their `project-type`, propose from the installed skills those
   that fit each project (for example an object-oriented design skill for
   object-oriented code, a UI design skill for a project with screens), and write the
   answers. A developer who gives no answer gets an empty key, which keeps the old
   behavior. Already done when every entry has the key.
2. **Managed blocks.** Nothing to do outside them: section 3 of `references/upgrade.md`
   re-renders the block `working-agreement` of root `AGENTS.md`, and inserts and
   re-renders the blocks `reqs-spec`, `reqs-size`, and `reqs-skills` of
   `reqs/AGENTS.md`.
3. **Request files and branches.** Change none. A request approved before this version
   has no "Sections from the project's skills": the lead review of
   `/ss-workflow:check-req` does not fault it for a section that did not exist.

## Check

- Every entry of `projects` in root `AGENTS.md` has the key `skills` (it may be empty).
- `reqs/AGENTS.md` contains the headings `## Request size` and `## Project skills`,
  and root `AGENTS.md` contains the bullet that starts "**Roles.**".
- No request file changed.
