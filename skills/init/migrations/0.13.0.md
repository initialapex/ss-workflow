# Migration to 0.13.0

## What changes

- **Every stage has a role.** Before: the skills did not say whose point of view each
  stage works from. Now: `/ss-workflow:new-req` is a requirements engineer,
  `/ss-workflow:check-req` is an engineering lead who reviews the request and then a
  software engineer who implements it, `/ss-workflow:init` is a software engineer who
  writes the initial spec, `/ss-workflow:review` is an engineering lead plus a UI and
  UX reviewer, and `/ss-workflow:merge` and `/ss-workflow:release` are a CI and CD
  engineer. Each skill states its role at its top, and "Working agreement" in root
  `AGENTS.md` lists them.
- **The engineering lead reviews a request before it starts.** Before:
  `/ss-workflow:check-req` created the branches and worktrees of a `ready` request at
  once. Now: it first checks the approved spec (complete, small enough, ordered after
  its dependencies, evidence in order, checkable), records `### Lead review` in
  `## Notes`, and offers to send a failing spec back to `/ss-workflow:new-req` or to
  start it anyway.
- **A request that is too large is split.** Before: `/ss-workflow:new-req` proposed a
  split only when the input held independent changes. Now: "Request size" in
  `reqs/AGENTS.md` gives the signals and the three axes (importance with must-fix
  first, type, cost), and `/ss-workflow:new-req` splits a request along them so that
  one request can be read and reviewed in one sitting. A part that needs another one
  starts its "Scope" with `Depends on: REQ-xxxx`.
- **A project can have a GUI, and its requests follow UI and UX rules.** Before: the
  workflow did not know whether a project has a GUI. Now: the project key `has-gui`
  (`yes` or `no`) says it. For a project with a GUI, "UI and UX" in `reqs/AGENTS.md`
  applies two principles that the skill `ss-design:ui-ux` defines (the same margin and padding for the same kind of element, taken
  from one spacing scale; visual guidance with one primary action, a reading and Tab
  order, visible states), "Detailed design" gets a "UI" section, and
  `/ss-workflow:review` adds a UI and UX review.
- **A project with a GUI has an operation manual.** Before: `docs/<name>/spec.md` was
  the only document of a project. Now: a project with `has-gui: yes` also has
  `docs/<name>/manual.html`, one HTML file that defines the behavior of every control
  of every view. Requests that change the GUI update it, and the Review reads its diff.

## Steps

1. **`has-gui` for every project.** For each entry in `projects` in root `AGENTS.md`
   that lacks the key, add `has-gui:` after `project-kind:`. Show the developer the
   list of the projects with their `project-type`, propose `yes` for a project that has
   a window, dialog, or page that a person operates, and `no` for a library, a service,
   a command-line tool, or firmware without a display, and write the answers. A
   developer who gives no answer gets `no`, which keeps the old behavior. Already done
   when every entry has the key.
2. **The documents of a project with a GUI.** For each project with `has-gui: yes`:
   - Create `docs/<name>/manual.html` from `templates/project-manual.html` (fill
     `{{ENTRY_NAME}}` and `{{ENTRY_DESCRIPTION}}`), unless it exists. Show it first:
     it is a new file in the developer's `docs/`. The first request that changes a view
     fills in the views that it touches.
   - Add the part "UI conventions" from `templates/project-spec.md` to
     `docs/<name>/spec.md` unless it has one. Read the existing views and styles of the
     project (read only), propose the spacing scale that they use, and write it with the
     developer's answer. Show the change first: the spec belongs to the developer.
   Already done when the manual exists and the spec has "UI conventions".
3. **Managed blocks.** Nothing to do outside them: section 3 of `references/upgrade.md`
   re-renders the block `working-agreement` of root `AGENTS.md`, and inserts and
   re-renders the blocks `reqs-spec`, `reqs-size`, and `reqs-ui` of `reqs/AGENTS.md`.
4. **Request files and branches.** Change none. A request approved before this version
   has no "UI" section: the lead review of `/ss-workflow:check-req` reports it for a GUI
   project when it starts, and the developer chooses to send it back or to start it
   anyway. A request that is in review keeps its record as it is.
