# Migration to 0.10.0

## What changes

- **Each kind of project tag has its own place.** Before: every version, the
  prereleases too, was released through `release/v<version>` (for example
  `release/v1.0.0-beta1`), merged into the project's main branch, and tagged there.
  Now:
  - A final version `vX.Y.Z` is tagged on the project's main branch only.
  - An alpha or beta version is tagged on the tip of the project's develop branch,
    with no release branch and no merge. The workspace tags the commit on `develop`
    that records it, `<name>/vX.Y.Z-betaR`. Only a project whose `version-source` is
    `git-tag` or `none` gets alpha and beta versions, because the tag cannot follow a
    version commit on the develop branch.
  - A release candidate `vX.Y.Z-rcR` is tagged on the release branch, which is now
    named after the final version (`release/v1.2.0`) and stays open through its
    release candidates. It has no workspace tag. Between two release candidates the
    project goes back to its gitlink, so the root checkout is free while a release
    candidate is tested. Small fixes go onto the release branch; larger changes go
    through a request into the develop branch, which is then merged into the release
    branch for the next release candidate. While a release branch is open, the
    develop branch gets no alpha or beta tag.
  - A final version does not need a release candidate first.
- **The main branch merges back into the develop branch.** Before: a release or
  hotfix branch was merged into the project's main branch and, separately, into its
  develop branch, so the tag on the main branch was not reachable from the develop
  branch. Now: after the tag, the main branch is merged into the develop branch (and,
  after a hotfix, into an open release branch). A build that reads its version from
  the nearest tags then finds the final version on the develop branch too. The first
  merge of this kind also brings the old merge commits of the main branch; their
  content is already on the develop branch, so a conflict is usually on the version
  number alone.
- **`version-source: git-tag`.** A new value: the build reads the version from the git
  tag and writes it into generated files that git ignores. A release then never
  commits a version number. A file and `none` work as before, apart from the alpha
  and beta rule above.
- **Tag first, then build and package, then publish.** Before: the release built the
  release branch, merged, tagged, and pushed each repository as it went, and offered
  a platform release at the end. Now: the release creates the tag locally, builds the
  tagged commit, runs the new `package-command`, and zips the files of the new
  `package-files` into `.claude/packages/<name>-v<version>.zip`. Only when all of it
  succeeded in every repository does it ask once and push everything, then create the
  platform release (a prerelease for alpha, beta, and release candidate versions) with
  the zip as its asset. With a merge request, the merge is public first, and the tag
  and the package follow it.
- **The hotfix version** is the next patch after the highest final tag that the
  project's main branch contains, not after the nearest tag: the main branch now
  contains the alpha and beta tags of the develop branch.

## Steps

1. **The package keys.** In root `AGENTS.md`, every entry of `projects` gets the keys
   `package-command:` and `package-files:`, after `verify-command`, empty. Empty keeps
   the old behavior: no package is made or uploaded. Then ask the developer, per
   project, whether to fill them now; propose values as the questionnaire's Round 3
   does (`references/questionnaire.md`): `package-files` lists the executables and
   libraries of the release build, as glob patterns relative to the project folder.
   Already done when every entry has both keys.
2. **`.gitignore`.** Add `.claude/packages/` to the ss-workflow block of the
   workspace's `.gitignore`, after `.claude/worktrees/`, with its comment line from
   `templates/gitignore.template`. Already done when the line is there.
3. **`version-source`.** Tell the developer about `git-tag`, and that alpha and beta
   versions need it (or `none`). Change nothing: a project keeps its value until the
   developer changes it.
4. **Open release branches.** For each project, list `git -C <path> branch -a --list
   "*release/*"`. A release branch named with a prerelease suffix
   (`release/v1.0.0-beta1`) was opened before this version: tell the developer. Its
   release merge asks whether to finish it as that version, the old way, or as the
   final `X.Y.Z`. Nothing changes now.

## Check

- Every entry of `projects` in root `AGENTS.md` has `package-command:` and
  `package-files:`.
- `git check-ignore -q .claude/packages/x.zip` succeeds in the workspace root.
- The managed blocks "Branching model", "Remote and pushing", and "Versioning" of root
  `AGENTS.md` describe where each kind of tag goes and the merge of the main branch
  back into the develop branch (section 3 of `references/upgrade.md` renders them).
