# Migration to 0.7.0

## What changes

- **Every project has its own docs folder.** Before: the workspace had one spec,
  `docs/<workspace slug>-spec.md` (for example `docs/ssdisp-workspace-spec.md`), and a
  project added later got no spec. A converted workspace could end up with two specs.
  Now: `docs/overview.md` describes the workspace as a whole (what the projects do
  together, how they depend on each other, shared terms), and `docs/<name>/` holds
  the docs of one project, with its spec in `docs/<name>/spec.md`. `/ss-workflow:init
  --add` creates the spec of a new project. The skills read the overview and the docs
  of the projects that a request touches, not every spec.
- **A request may change workspace files.** Before: the workspace request branch only
  held the request file and the gitlinks, so a request could not update a spec in
  `docs/`, although the rules asked for it. Now: the workspace request branch also
  holds the request's changes to the docs, the README files, `.gitignore`, and the
  text of the agent files outside their managed blocks (for example "Project notes"
  or a `## Project: <name>` section). Managed blocks, `ss-workflow-version`,
  `.gitmodules`, and the `projects` entries stay out of requests. These changes are
  not built or code-reviewed: the developer reads each of them in the Review.
- **A request may change workspace files only.** Before: a request with an empty
  `projects` could not be approved, so a docs-only change had no way through the
  workflow. Now: `projects: []` is such a request. It has a workspace branch and no
  project branch, Verify has nothing to run, the Review covers all of it, and no
  project release counts it.
- **Releases update the workspace docs before the workspace main branch.** Before:
  places in the workspace's `docs/` that state a project's version were changed on
  `develop` after the release merge, so the workspace main branch still showed the
  old version. Now: the release merge changes them on `develop` before it merges into
  the main branch, and a hotfix changes them on its workspace branch.
- **Requests from before the conversion name their project.** Before: a request file
  without `projects` belonged to "the one project that the repository had", which was
  recorded nowhere once a second project was added. Now: the setting
  `legacy-project` names it.

## Steps

1. **Settings** in root `AGENTS.md`, block "Workflow settings":
   - Add `legacy-project:` on the line after `agent-files:`.
   - Its value: if the workspace was converted from the single-repository layout,
     the project of that conversion. Find it in the commit
     `chore(workspace): import the requests of <name>`
     (`git log --format=%s develop | grep "import the requests of"`), or, failing
     that, ask the developer which project the request files without `projects`
     belong to. Otherwise leave it empty, without a trailing space. Needs the
     developer's answer when it is not empty.
   - Below the settings, add the sentences of the template that explain
     `legacy-project` (they start with "`legacy-project` names the project"). This
     text is outside the managed blocks, so show it to the developer.
   - Already done when the key exists.
2. **Docs**: list the files in `docs/`, and propose a table of old and new paths:
   - The spec that init created for the workspace (`docs/<workspace slug>-spec.md`,
     the one whose "Architecture" describes the projects of the workspace) becomes
     `docs/overview.md`. Its sections stay as they are; the developer may reorder them
     later.
   - A spec of one project, for example `docs/<project slug>-spec.md` from a
     conversion, becomes `docs/<name>/spec.md`.
   - Other files: ask whether each one is about one project (into `docs/<name>/`, with
     the same relative path) or about the workspace (stays in `docs/`).
   - Each project that has no spec after this gets `docs/<name>/spec.md` from
     `templates/project-spec.md`. If no file becomes the overview, create
     `docs/overview.md` from `templates/docs-overview.md`. Fill its "Projects" with
     one line per project.

   Everything in `docs/` belongs to the developer, so show the table and get an
   answer before you move anything. Move with `git mv`, so that git records each move
   as a rename. Then fix the links to the moved files: in the README files, in
   `docs/`, and in "Project notes" of root `AGENTS.md`. If the developer declines,
   leave the files where they are: the skills then say that `docs/overview.md` or a
   project's spec is missing, and the health check offers this step again.
   Already done when `docs/overview.md` and a `docs/<name>/spec.md` for every project
   exist.
3. **README files**: the project table of each root README gets a column for the
   spec, after the repository column (`Spec` in `README.md`, `規格` in
   `README-zh-TW.md`), with the link `` [`docs/<name>/spec.md`](docs/<name>/spec.md) ``
   in each row. "Documentation" links to `docs/overview.md` instead of the old spec.
   These files belong to the developer: show the change, and get an answer. Already
   done when the table has the column.
4. **"Repository layout"** in root `AGENTS.md`: replace the row of `docs/` with the two
   rows of the template (`docs/overview.md` and `docs/<name>/`). This section belongs
   to the developer: show the change, and get an answer. Already done when the table
   has a row for `docs/overview.md`.
5. **Managed blocks**: the upgrade re-renders "Workspace and projects" in root
   `AGENTS.md`, "Rules" in `src/AGENTS.md`, and "Request file format", "Results and
   behavior changes", and "Lifecycle" in `reqs/AGENTS.md`. Nothing to do here.
6. **Request files**: do not change them. Open requests keep their `projects`. A
   request that is claimed already may update the docs on its workspace branch from
   now on; its implementation summary says so.

## Check

- `legacy-project:` exists in "Workflow settings" of root `AGENTS.md`, and it is empty
  or the `name` of an entry in `projects`.
- `docs/overview.md` exists, and `docs/<name>/spec.md` exists for every entry in
  `projects`, unless the developer declined step 2.
- `git log --follow --oneline -- docs/<name>/spec.md` still shows the history of a
  moved spec.
- `git status --porcelain -- reqs/` shows no changed request file, only
  `reqs/AGENTS.md`.
