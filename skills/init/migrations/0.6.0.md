# Migration to 0.6.0

## What changes

- **The repository becomes a workspace, and the code moves into its own repository.**
  Before: one repository held the code in `src/`, `tests/`, and `samples/`, and the
  requests in `reqs/`. Now: a workspace repository holds `reqs/`, `docs/`, the agent
  files, and the settings, and each project is a git submodule at `src/<name>`, with
  its own repository and the layout of its toolchain. The old repository becomes that
  project repository: it keeps its remote, its history, and its tags, and loses the
  workflow files. There is no `tests/`, `samples/`, or `external/` in the workspace.
- **Project commits are only implementation.** Before: request files, spec
  discussions, and review results were committed next to the code. Now: they are
  committed in the workspace only. A project commit ends with
  `Refs: <workspace>#REQ-xxxx`, a workspace commit with `Refs: REQ-xxxx`.
- **A request has two layers of branches.** Before: one request branch and one
  worktree. Now: the workspace branch is the claim; after it, each project of the
  request gets a branch with the same name. The worktree of a request holds a
  worktree of each project inside it. Verify, Review, and merge check out both
  layers, and a merge goes project by project, then the workspace.
- **Each project has its own version.** Before: one version for the repository, and a
  release raised it even for parts that did not change. Now: `/ss-workflow:release
  <project>` releases one project, tagged `v<version>` in its repository and
  `<project>/v<version>` in the workspace. The workspace main branch is the set of the
  latest released projects.
- **Settings are per project.** Before: `source-dir`, `project-file`,
  `version-source`, and the commands were settings of the repository. Now: they are
  keys of each entry in `projects`, with paths relative to the project folder and
  commands that run in it. A project may override `remote-platform`, `merge-method`,
  and `push-policy`. `project-type` and `project-kind` moved into the entries too.
- **Request files name their projects.** A new frontmatter key `projects` lists them.
  A request from before the conversion without it belongs to the one project.
- **Projects can be added later.** `/ss-workflow:init --add <url|path>` adds a project
  to the workspace, from a remote URL or a local git path.

## Steps

This migration cannot keep the old behavior: the skills of 0.6.0 only work in a
workspace. It needs the developer's answers throughout, and if the developer declines,
the upgrade stops and nothing changes.

1. Follow [../references/convert-legacy.md](../references/convert-legacy.md),
   sections 1 to 9. It checks that no work is in progress, restores the toolchain's
   layout in the old repository and removes the workflow files there, creates the
   workspace with the old repository as its project, and moves the requests, the
   drafts, and the docs. Each of its sections says how to tell that it is already
   done.
2. The workspace is created from the current templates, so its managed blocks and its
   `ss-workflow-version` are current. Do not upgrade the old repository's managed
   blocks: its workflow files are removed.
3. Request files: the files in `reqs/done/` are copied byte for byte. Each `ready`
   request and each draft gets `projects: [<name>]` after `type:`, and nothing else.
   Requests that were claimed cannot be converted: the preconditions require that
   they are finished first.

## Check

- In the old repository, `develop` has no `reqs/` folder and no ss-workflow
  `AGENTS.md`, and `git log --follow` still shows the history of a moved file.
- The workspace's root `AGENTS.md` has `ss-workflow-version:` with the plugin version,
  and a `projects` entry whose `path` is in `.gitmodules`.
- `git -C <workspace> ls-tree -r --name-only develop reqs/` lists every request file
  of the old `develop`, and the workspace has a `req/` branch for each old draft.
- `git -C <workspace> submodule status` shows the project initialized, and the
  project builds with its `build-command` in its folder.
