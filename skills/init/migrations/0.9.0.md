# Migration to 0.9.0

## What changes

- **The projects live in `projects/` instead of `src/`.** Before: each project was a
  submodule at `src/<name>`, and the rules of the projects were in `src/AGENTS.md`.
  Now: `projects/<name>` and `projects/AGENTS.md`. A project does not have to be
  source code: it can be a repository of documents or analysis reports, and `src/`
  suggested otherwise. The skills read each project's folder from its `path` in
  "Workflow settings", so nothing else about how they work changes.
- **The managed block of `projects/AGENTS.md` has a new id**: `projects-rules`
  instead of `src-rules`.

## Steps

This upgrade moves submodules, so it runs only when no request is in the middle of
its implementation or review. The steps change the main branch once outside a
release: that commit moves the projects and changes no gitlink. The move needs the
developer's approval, because every clone of the workspace sees it.

1. **Preconditions.** Check, and stop with a list of what was found if any fails:
   - The root checkout is on `develop`, and `git status --porcelain` is empty.
   - No request is started and not merged: no request branch whose request file
     says `in-progress`, `review`, or `done` while the branch is not merged into
     `develop` (collect them as `/ss-workflow:check-req` does in its overview).
   - No `release/*` branch in any project, and no `hotfix/*` branch in the workspace.
   - `git worktree list` shows the root checkout only.

   Drafts and `ready` requests do not block: step 5 brings their branches along. If
   the preconditions fail, the developer finishes that work first with
   `/ss-workflow:review` and `/ss-workflow:merge`, and runs `/ss-workflow:init`
   again. Until then the skills keep working, because they take each project's
   folder from its `path`; where a skill names `projects/AGENTS.md`, read
   `src/AGENTS.md`.

   Already done when the root `AGENTS.md` has no `path: src/` and `src/AGENTS.md`
   does not exist on `develop`.
2. **Show the plan and ask.** List each move (`src/<name>` → `projects/<name>`,
   `src/AGENTS.md` → `projects/AGENTS.md`), any other file in `src/` (ask where it
   goes), and the hits of `grep -rn "src/" README*.md docs/ AGENTS.md` outside the
   managed blocks, such as the project table of the README files, links in the docs,
   "Project notes", or an `agent-files` pattern. Those texts belong to the developer:
   propose the new text for each hit. Continue only when the developer agrees.
3. **Move on `develop`**, in the root checkout:

   ```bash
   mkdir projects                               # git mv does not create the folder
   git mv src/<name> projects/<name>            # each project
   git mv src/AGENTS.md projects/AGENTS.md
   ```

   Then, in the same commit:
   - Root `AGENTS.md`, "Workflow settings": `path: projects/<name>` in every entry
     of `projects`, and `projects/` in `agent-files` patterns that named `src/`.
   - `projects/AGENTS.md`: the heading `# projects/` and the marker
     `<!-- ss-workflow:managed id=projects-rules -->`. The upgrade re-renders the
     block afterwards.
   - The texts that the developer approved in step 2.

   Commit `chore(workspace): move the projects to projects/`, and remove the empty
   `src` folder if one is left. `.gitmodules` now has `path = projects/<name>`; each
   submodule keeps its name (`[submodule "src/<name>"]`) and its git folder in
   `.git/modules/src/<name>`. That is expected, and git needs nothing else.
4. **Move on the main branch**, in a temporary worktree, never by switching the root
   checkout (git would leave the populated `projects/<name>` folders behind and
   mix the two layouts):

   ```bash
   git worktree add .claude/worktrees/upgrade-<main branch> <main branch>
   ```

   In it, make the same move as in step 3 (the submodule folders there are empty,
   which is fine), with the same commit message, and then
   `git worktree remove .claude/worktrees/upgrade-<main branch>`. The gitlinks keep
   their commits: the main branch still records the latest release of each project.
   The next release merges `develop` into the main branch as usual; its
   `git update-index --cacheinfo` resolves the gitlinks on the new paths.
5. **Open request branches** (drafts and `ready` requests, and `req/*` drafts from
   before 0.8.0) still have the old layout, and a worktree started from one would put
   the projects in `src/`. Bring each one along without switching the root checkout:

   ```bash
   git worktree add .claude/worktrees/upgrade-<id> <branch>
   git -C .claude/worktrees/upgrade-<id> merge --no-ff develop -m "Merge develop into <branch>"
   git worktree remove .claude/worktrees/upgrade-<id>
   ```

   These branches change only their request file, so the merge has no conflicts. If
   one has a conflict, abort it and report the branch. This is the one migration step
   that touches request branches: a layout change cannot wait for the next skill that
   writes the file.
6. **Push** `develop` and the request branches as `push-policy` allows. Pushing the
   main branch asks first, as always.
7. **Other clones.** Tell the developer what other clones of the workspace see after
   `git pull` and `git submodule update`: the projects are in `projects/`, and the old
   `src/<name>` folders stay behind as untracked files (`?? src/`). Before deleting
   one, check `git -C src/<name> status --porcelain`: uncommitted changes there are
   only in that folder. Commits are safe either way: they are stored in
   `.git/modules/`.

## Check

- `git ls-tree -r --name-only develop | grep -c '^src/'` and the same for the main
  branch print `0`.
- `git config -f .gitmodules --get-regexp 'submodule\..*\.path'` lists only
  `projects/<name>` paths, one for each entry in `projects`.
- `git rev-parse <main branch>:projects/<name>` is the same commit as before the
  move, for every project.
- `git -C projects/<name> status` works for every project, and the root checkout is
  clean.
- Every open request branch contains `develop`
  (`git merge-base --is-ancestor develop <branch>`).
