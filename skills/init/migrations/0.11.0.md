# Migration to 0.11.0

## What changes

- **A spec has to make the implementations converge.** Before: the spec settled what a
  user sees ("Scope") and the architecture ("Architecture"), and left everything below
  that, such as the names of functions and the layout of a file, to the
  implementation. Now: a spec is complete only when anyone who implements it from the
  spec and the repository alone, a senior engineer, a junior engineer, or another
  agent, builds almost the same thing. `reqs/AGENTS.md` gets a section "Spec" that
  describes the standard and the parts of `## Spec`.
- **A new part "Detailed design"**, after "Architecture", with fixed sections: File
  changes, Types and public members, Data and state, Flows, Errors and edge cases,
  Configuration and dependencies, Tests, and Left to the implementation. Public members
  are listed with their names, parameters, and types; members that only a type itself
  uses are left to the implementation. A small change gets a short detailed design,
  never none.
- **No code in the spec.** Before: nothing was said about it. Now: the spec holds no
  program code and no pseudo-code. Types, members, and flows are described in tables
  and plain sentences, with every name written out. Examples of data formats and of
  commands that a user types are still allowed.
- **A cold read before the approval.** `/ss-workflow:new-req` has a fresh subagent,
  which knows nothing of the discussion, read `## Spec` and the code, and list every
  place where an implementer would have to guess. The findings become spec fixes or
  `## Q&A` entries before the developer approves. The result goes into `## Notes` as
  `### Cold read`.
- **The implementation follows the detailed design.** `/ss-workflow:check-req` plans
  and builds from "File changes" and the other sections, decides on its own only what
  "Left to the implementation" names, and stops and asks about every other decision
  that the spec does not settle. A request that is `ready` or `in-progress` and has no
  "Detailed design" gets one, confirmed by the developer, before the implementation
  goes on.
- **A design check in the review.** `/ss-workflow:review` compares the changes with
  "Detailed design" and lists every deviation. The developer decides on each one: fix
  it, or accept it, which updates the spec. The result goes into `## Notes` as
  `### Design check`. A request that was implemented without a detailed design records
  the check as not applicable.

## Steps

1. **`reqs/AGENTS.md`.** Nothing to do outside the managed blocks: section 3 of
   `references/upgrade.md` inserts the new block `reqs-spec` ("Spec") after the block
   `reqs-format`, and re-renders `reqs-format` and `reqs-results`, whose comments and
   text now name the new part and the new results. Already done when the file has the
   block `reqs-spec`.
2. **Request files.** Change none. A draft gets its "Detailed design" when
   `/ss-workflow:new-req` continues it, and a `ready` or `in-progress` request when
   `/ss-workflow:check-req` starts or resumes it. Tell the developer which requests are
   affected: the request branches whose request file says `draft`, `ready`, or
   `in-progress`, collected as `/ss-workflow:check-req` does in its overview.

## Check

  the block `reqs-format`.
- The comment under `## Spec` in the format of the block `reqs-format` names the
  detailed design.
- No request file changed.
